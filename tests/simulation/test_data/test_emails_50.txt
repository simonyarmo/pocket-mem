We had our first real incident on the new Nightwatch stack last night. Full postmortem below.

Timeline:
- 11:43 PM — Alertmanager fired disk space alert on the TimescaleDB node (85% full)
- 11:51 PM — I received the page and acknowledged
- 11:58 PM — Root cause identified: Conduit test data from the backfill validation runs wasn't being pruned
- 12:30 AM — Pruning job run manually, disk space back to 41%, alert resolved

Fix applied: updated the pruning job to run daily instead of weekly, and added a post-backfill cleanup step to the runbook.

Incident metrics:
- Time to page: 8 minutes (within our 15-minute SLA)
- Time to resolution: 47 minutes total
- Impact to users: none (disk never reached 95% threshold that would affect writes)

Darnell,

Found something while writing additional test coverage for the consumer workers.

When a Kafka consumer rebalances (consumer group membership changes — e.g., a pod restarts), there's a window where the same batch of events can be processed twice. The consumer workers don't have idempotency keys, so duplicate events can be written to TimescaleDB.

I ran some numbers: based on the rebalance frequency in production logs, this probably affects less than 0.01% of events. But at 180k events/hour, that's potentially ~180 duplicate events per hour.

Proposed fix: add an idempotency key column to the events table and check for duplicates on insert. I've drafted the implementation — can you review?
